# Phase 23 Plan 01: Lift float<->int16 Boundary into BoundaryConverter Module

Lift the inline `f32_to_s16` / `s16_to_f32` anonymous-namespace lambdas currently embedded in `src/plugin/SrcChain.cpp:45-56` into an explicit, named, header-only module: `src/plugin/BoundaryConverter.h`, exposing two free functions `spu94::plugin::boundary::toInt16(float)` and `::toFloat(int16_t)`. Net behavior: **zero audible change**. The converter is byte-identical to the existing inline implementations — same multiply, same clamp range, same truncation, same no-dither North Star contract.

This plan exists for two reasons:
1. **Tests & responsibility surface.** The float↔int16 boundary is the only place audible distortion is introduced on the input side of the plugin. A named module gives it a home for unit tests and a single grep-able call site for the saturation gate verification step (PLUG-18). Today, that math is buried inside SrcChain alongside libsamplerate plumbing — wrong neighborhood.
2. **Plan 02 needs a clear seam.** Plan 02 (Wave 2) repositions the Input Gain to a pre-clamp float multiply. That repositioning is much cleaner when the clamp itself is a named function, not an inline lambda. Plan 01 leaves the door open; Plan 02 walks through it.

The C core (`libspu94`) and its internal `sat_s16` (ADR-0001) are not touched. The standalone testbed path's inline `/ 32768.0f` divisions at `PluginProcessor.cpp:398-399` are also not touched — standalone is internal dev-only per v1.7, the inline math is correct, and changing it expands diff surface for no behavior change.

## Rationale

Phase 22 left a clean seam intentionally — see 22-PLAN.md's Phase 23 note: *"Phase 23 will slot the float↔int16 converter into the SRC sandwich; Phase 22 leaves a clean integration point and no architectural debt."* This plan claims that seam.

What this plan decides:
- **Module home:** `src/plugin/BoundaryConverter.h` (sibling to `SrcChain.h`, plugin-only). NOT in `c_core/spu94/include/`. Rationale recorded in `boundary_decisions.module_home`.
- **Module shape:** Two free `inline noexcept` functions in `namespace spu94::plugin::boundary`. Stateless, header-only. Rationale recorded in `boundary_decisions.module_shape`.
- **Standalone-path parity:** Standalone keeps its inline `/ 32768.0f` divisions. Recorded as a (small, optional) follow-up in the SUMMARY's deferred items.

```
  │  if isFastPath_:                                            │

        │
        ▼ side-channel limiter (PluginProcessor.cpp:469-478, untouched)
        ▼ host audio (float, host_SR)
```

The boundary boxes are the only thing that changes in Plan 01 — and they change in name only.

### Public surface

```
namespace spu94::plugin::boundary {
    // Float [-1.0, +1.0] -> int16 [-32768, +32767], clamp+truncate.
    // Out-of-range inputs saturate (sat_s16 semantics, ADR-0001).
    // No dither, no rounding. Truncation = static_cast<int16_t>.
    inline int16_t toInt16(float x) noexcept;

    // int16 [-32768, +32767] -> float by divide by 32768.0f.
    // Maps -32768 to -1.0f exactly; maps +32767 to +0.99996948... (not
    // +1.0). Preserves the existing inline semantics byte-identically.
    inline float   toFloat(int16_t x) noexcept;
}
```

### Saturation gate (PLUG-18)

The function body MUST be structurally equivalent to the lifted lambda:

1. Multiply `x` by `32768.0f` into a float `y`.
2. If `y >= 32767.0f`, return `32767`.
3. If `y <= -32768.0f`, return `-32768`.
4. Otherwise, return `static_cast<int16_t>(y)`.

A `static_assert` block in the header exercises the four corner cases at compile time where possible, and an inline self-check `[[maybe_unused]] constexpr` test exercises them at runtime if the compiler can't fold them (the multiply-then-branch isn't constant-evaluable on all toolchains — the executor decides whether to gate behind `if constexpr` or fall back to a runtime `assert` in a `[[maybe_unused]]` lambda).

```
    using namespace spu94::plugin::boundary;
    std::printf("%d %d %d %d\n",
```
