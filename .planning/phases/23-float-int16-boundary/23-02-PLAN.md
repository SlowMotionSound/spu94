# Phase 23 Plan 02: Reposition Input Gain Pre-Clamp + Extend Drive Range

Move the plugin path's Input Gain from a post-clamp engine-register multiply (`spu94_set_input_gain` writing a Q15 value into the C core) to a pre-clamp **float multiply on the host-rate signal**, applied before the SRC sandwich and before `BoundaryConverter::toInt16`'s clamp. Extend the parameter's internal range from `0.0..1.0` to `0.0..~16.0` (+24 dB ceiling). Default stays at `0.5` (-6 dB), which now genuinely means -6 dB of headroom below the int16 ceiling.

This is the audible-behavior plan of Phase 23. Where Plan 01 lifted a named seam (zero audible change), Plan 02 walks through it (D-01 + D-02). The combination turns Input Gain from a passive trim into a character control:

- **0.0 → silence.**
- **0.5 (default) → -6 dB.** Real headroom; the boundary clamp is below the signal floor, not clipping anything.
- **1.0 → unity.** A 0 dBFS sine passes through with zero saturation.
- **~16.0 (knob ceiling) → +24 dB drive.** Drives any non-silent signal hard into `sat_s16`, turning the boundary into a deliberate saturator/overdrive stage. Recording-engineer framing: this is the "fuzz pedal" zone the user picked in the discussion.

The C core is not modified. The `spu94_set_input_gain` register still exists and still does its thing on the standalone path and in C-core test programs; only the PLUGIN PATH'S USE of it changes (pinned at unity, D-03 resolved). The side-channel limiter at `PluginProcessor.cpp:352-405` and `:465-478` is byte-identical before and after (PLUG-20 gate).

## Rationale

Pre-clamp placement is the only placement that makes Input Gain a coherent knob. With the previous post-clamp engine-register placement:
- Turning the knob down didn't actually give the user headroom: the signal was already clipped at the boundary; the engine register just attenuated the clipped result.
- Turning the knob up couldn't drive into the boundary clamp: the register was downstream of the clamp.

After D-01 + D-02 the knob is honest in both directions. Below unity it attenuates BEFORE clip — the boundary clamp is "out of reach" until the input itself is hot. Above unity it deliberately drives into the clamp — `sat_s16` becomes a feature, not a hazard.

D-03 (engine register handling): **pinned at unity on the plugin path.** Two gain stages on the same knob is a foot-gun. One gain stage where the user can see what's happening matches the North Star ("fixed-point quirks ARE the product" — user should reach the quirks directly, not through accidental cascaded register math).

Standalone-path parity is deliberately not pursued: standalone is internal dev-only per v1.7, the existing engine-register behavior is correct for its use case, and migrating it expands diff surface for zero v1.7 deliverable benefit. Captured as a small follow-up in `input_gain_decisions.standalone_path`.

## Design

### Plugin-path topology (after this plan)

```
  host audio (float, host_SR)
        │
        ▼ const float gain = inputLevel.load(relaxed);   // [0.0..~16.0]
        ▼ for i: scratch[i] = host[i] * gain;            // pre-clamp float multiply
        │
        ▼ srcChain_.processIn(scratch ptrs, n, coreInL, coreInR, coreN)
        │  ├─ SRC host_SR → 44100 (libsamplerate, non-fast-path)
        │  └─ BoundaryConverter::toInt16(...)            // <-- clamp+truncate here, sat_s16 active
        │
        ▼ int16 @ 44100 Hz
   spu94_set_input_gain(engines[0], 0x7FFF);             // pinned at unity, plugin path only
   spu94_process(engines[0], coreInL, coreInR, coreOutL, coreOutR, coreN)
        │
        ▼ int16 @ 44100 Hz
        ▼ srcChain_.processOut(...) → BoundaryConverter::toFloat → SRC 44100→host_SR
        │
        ▼ side-channel limiter (PluginProcessor.cpp:465-478, UNTOUCHED)
        ▼ host audio (float, host_SR)
```

### Atomic semantics (PluginProcessor.h:148)

The literal initializer is preserved byte-identically — `{0.50f}` stays for the PLUG-19 gate. Only the inline comment is updated to document the new range:

```
// inputLevel: pre-clamp float gain factor on the plugin path.
// Range 0.0..16.0 (linear). Anchor points:
//   0.0  -> silence
//   0.5  -> -6 dB  (default; -6 dB headroom below int16 ceiling)
//   1.0  -> unity
//   16.0 -> +24 dB drive (intentionally clamps via sat_s16, North Star quirk)
// Standalone path still applies this value as a Q15 engine register
// at :264-265; that path is unchanged (internal testbed only).
std::atomic<float> inputLevel{0.50f};

// Public anchors for Phase 24 (AudioProcessorParameter wiring).
static constexpr float kInputGainDefault = 0.5f;
static constexpr float kInputGainMax     = 16.0f;
```

### Scratch buffer strategy

Allocate a per-channel `juce::HeapBlock<float> inputGainScratch_[2]` on `SPU94AudioProcessor`, sized in `prepareToPlay` to `kMaxBlock = 4096` samples. The plugin branch fills `inputGainScratch_[ch][i] = buffer.getReadPointer(ch)[i] * gain`, then hands `inputGainScratch_[0..1].getData()` to `srcChain_.processIn` (via the `hostInPtrs` array). No host buffer mutation, no per-block allocation, no syscalls.

Alternative considered: `juce::FloatVectorOperations::multiply(buffer.getWritePointer(ch), gain, n)` in place on the host buffer. Rejected as the default because not all wrapper types guarantee writable input (AAX, some CLAP hosts). The scratch path is safer; the executor MAY choose the in-place path if they verify it's safe across all 4 plugin formats, and document the choice.

### Preset round-trip note

`savePresetToString` (`PluginProcessor.cpp:484-524`) currently syncs the atomic to the engine register at :491-492 before calling `spu94_preset_save`. On the plugin path, this sync now writes `0x7FFF` (unity) regardless of the atomic's value. Consequence: a plugin-saved preset's stored `input_gain` is always unity. The GUI's Input Gain knob position is NOT stored in the preset under v1.7 (the preset captures C-core engine state; the plugin's float gain factor lives in `inputLevel`, which is host-automation state that the host saves separately as part of the plugin's APVTS state — Phase 24 work).

Cross-path preset divergence: a v1.6 standalone preset with stored `input_gain = 0x4000` (~0.5 in Q15) loaded into the plugin will set the engine register to 0x4000, but the plugin path immediately overwrites it to 0x7FFF every block. The plugin's actual gain comes from the GUI atomic. This is the documented D-03 trade-off.

### Audible behavior gates (manual UAT)

Two render passes through the LV2 plugin at 48 kHz host SR, Dry=1.0, Reverb=0.0, ADPCM=0.0, ScopedNoDenormals active:

1. **Headroom test (Input Gain = 0.5, default):** input = 5 s of 1 kHz 0 dBFS sine. Output should be a clean -6 dB sine. Measured RMS ≈ -9 dBFS (-6 dB peak corresponds to -9 dBFS RMS for a sine). THD < 0.01% relative to an ideal -6 dB reference sine (ignoring SRC sinc-tap rolloff and DAC coloration). NO boundary clamp engaged.

2. **Drive test (Input Gain = 16.0, ceiling):** same 0 dBFS sine input. Output should be a hard-clipped near-square waveform at full-scale (peak at -0.0 dBFS, sustained), THD > 10%, audibly distorted. This is the saturator/overdrive character — the deliberate D-02 behavior.

If (1) shows distortion, the pre-clamp multiply isn't actually pre-clamp (regression). If (2) shows clean attenuated output, the +24 dB ceiling isn't actually reaching the clamp (regression).
