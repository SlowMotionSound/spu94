<objective>
Implement the stereo widener as a static L/R volume offset on voice 0 in processBlock.
Width knob (0-100%) controls how much vol_l and vol_r diverge from their base pan
position. A mono-safety cap limits divergence so that summing L+R to mono loses no
more than ~3 dB at maximum width.

Purpose: Creates perceived stereo width by making left and right channels differ in
level. Simple, static, and mono-compatible — no sweep machinery needed, just an
offset applied to the existing vol_l/vol_r values each tick.

Output: Width atomic on the processor, offset calculation in processBlock, integration
test proving the mono-safety cap holds.
</objective>

  3. Mono-safety cap derivation:
     The mono-safety cap ensures that when L and R are summed, the result is no more than ~3 dB below what a centered (equal L/R) signal would produce.

     For a centered signal: vol_l = vol_r = V. Mono sum = vol_l + vol_r = 2V.
     With width offset: vol_l = V + offset, vol_r = V - offset. Mono sum = 2V (unchanged!).

     Wait — simple additive offset does NOT reduce mono sum. The mono sum is always vol_l + vol_r = (V + offset) + (V - offset) = 2V regardless of offset. So the widener is perfectly mono-safe for additive offset!

     BUT: if vol_l clips at 0x3FFF (the max), then the actual mono sum becomes less than 2V because the excess above max is lost. So the mono-safety concern is about CLIPPING the louder channel.

     To maintain the ~3 dB cap: the louder channel should not exceed its current value by more than the amount that would cause the clipped mono sum to be 3 dB down. In practice, cap the offset so that:
     - max_offset = min(0x2000, abs(current_vol)) -- limits divergence to ~50% of current level
     - This means the louder channel is at 1.5x and quieter at 0.5x; mono = 1.5x + 0.5x = 2x (full mono sum preserved)

     Actually, the cleanest approach for the PS1 volume range (-0x4000..+0x3FFF):
     - offset = (int16_t)(width * max_offset)
     - max_offset is capped so that (base_vol + offset) does NOT exceed 0x3FFF
     - If base_vol is already at 0x3FFF, the offset can only ADD to L by increasing it toward 0x3FFF (already there) and SUBTRACTING from R
     - The real mono-loss scenario: if the signal is panned center (vol_l = vol_r = 0x3FFF) and we add width, L stays clamped at 0x3FFF and R drops. Mono sum = 0x3FFF + (0x3FFF - offset) = 2*0x3FFF - offset. Loss = offset / (2*0x3FFF). For 3 dB loss: offset = 2*0x3FFF * (1 - 10^(-3/20)) = 2*0x3FFF * 0.292 ~ 0x2530.

     Implement as:
     - kWidthMaxOffset = 0x2000 (conservative: ~25% of full range, guarantees < 3 dB mono loss in all cases)
     - offset = (int16_t)(width * kWidthMaxOffset)
     - vol_l = clamp(vol_l + offset, -0x4000, 0x3FFF)
     - vol_r = clamp(vol_r - offset, -0x4000, 0x3FFF)

     With kWidthMaxOffset = 0x2000 (8192):
     - Worst case: both at 0x3FFF (16383). L clamps to 0x3FFF, R drops to 0x3FFF - 0x2000 = 0x1FFF.
     - Mono sum = 0x3FFF + 0x1FFF = 0x5FFE vs ideal 0x7FFE. Loss = 0x2000/0x7FFE ~ 0.25 = -2.5 dB. Within cap.
     - In normal panned positions where vol < 0x3FFF, no clipping occurs and mono sum is perfectly preserved (offset + anti-offset = 0).

  4. Placement in processBlock: AFTER all sweep-based effects (tremolo depth, auto-pan depth, and duck state machine) have finished writing vol_l/vol_r, AND after the GUI pan/level write. The width offset is the LAST thing that touches vol_l/vol_r before the voice_mixer_tick runs.

     Location: In the standalone path, after the auto-pan depth scaling block (around line 990) and after the duck state machine block (around line 1216), just before the marker-position update block. Add:

     ```
     // Stereo widener: static L/R divergence (WIDE-01, WIDE-02, WIDE-03)
     {
         float width = stereoWidth.load(std::memory_order_relaxed);
         if (width > 0.0f)
         {
             if (width > 1.0f) width = 1.0f;
             constexpr int16_t kWidthMaxOffset = 0x2000; // ~-2.5 dB mono loss at max
             int16_t offset = (int16_t)(width * kWidthMaxOffset);
             auto* mx = spu94_get_voice_mixer();
             int32_t new_l = (int32_t)mx->voices[0].vol_l + offset;
             int32_t new_r = (int32_t)mx->voices[0].vol_r - offset;
             // Clamp to PS1 volume register range
             if (new_l > 0x3FFF) new_l = 0x3FFF;
             if (new_l < -0x4000) new_l = -0x4000;
             if (new_r > 0x3FFF) new_r = 0x3FFF;
             if (new_r < -0x4000) new_r = -0x4000;
             mx->voices[0].vol_l = (int16_t)new_l;
             mx->voices[0].vol_r = (int16_t)new_r;
         }
     }
     ```

  5. Coexistence: The widener does NOT conflict with tremolo/auto-pan because it is applied AFTER those effects write their depth-scaled values. The sweep modulates vol to some level, then the widener pushes L up and R down from wherever they landed. This creates width on top of the sweep modulation. No mutual exclusion needed — the effects compose naturally.

     However, the widener DOES need to be careful about the duck state machine. If the voice is being ducked (vol dropping to near-zero), the width offset should still apply — it just won't matter much at low volumes. No special handling needed.

  6. The widener also works correctly with signed volume (negative vol = phase inversion). If vol_l is -0x2000 (inverted) and we add offset, it moves toward zero (less inverted). This is the expected behavior — width still diverges the channels.
