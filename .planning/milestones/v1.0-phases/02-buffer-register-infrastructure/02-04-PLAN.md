**BufferAddress arithmetic (RESEARCH.md § BufferAddress Arithmetic, research-confirmed):**

```
buffer_address = MAX(mBASE, (buffer_address + 2) AND 0x7FFFE)
```

- `buffer_address` is a `uint32_t` byte offset into SPU RAM.
- `0x7FFFE = 524286 = 0b0111_1111_1111_1111_1110`. Bit 0 clear (halfword alignment), top bit of a 19-bit address window (512 KB SPU RAM - 2 bytes).
- `mBASE` is the reverb-block base address; per Plan 03 it is a `u16` register stored as `int16_t` in `reg_values[SPU94_REG_mBASE]` (bit-reinterpreted). To interpret as an address, convert: `uint16_t mbase_u = (uint16_t)state->reg_values[SPU94_REG_mBASE];` and then treat as a byte address (same convention the nocash formula uses — the halved-by-8 convention for `m*` register values is NOT applied to `mBASE` in this context; that halving is a Phase 3 concern for consuming `m*` register values against the work buffer).
- The formula runs once per `spu94_tick()` call.

**mBASE snap-on-write (ADR-0006 per research primary-source citation):**

```
On any spu94_set_mBASE(state, new_mbase):
    state->reg_values[SPU94_REG_mBASE] = (int16_t)new_mbase;  (done by Plan 03 engine layer)
    state->buffer_address = (uint32_t)new_mbase;              (done here — this plan)
```

No implicit buffer clear. The jump can produce audible discontinuity; that is hardware-accurate.

```c
#include "spu94_state_internal.h"
#include <spu94/spu94.h>
#include <spu94/spu94_registers.h>
#include <stdint.h>

/* BufferAddress wrap formula (CORE-03, per psx-spx; see ADR-0006 and
 * RESEARCH.md § BufferAddress Arithmetic):
 *
 *     buffer_address = MAX(mBASE, (buffer_address + 2) AND 0x7FFFE)
 *
 * Called once per stereo tick from spu94_tick, AFTER pending writes
 * are applied (so mBASE is its latest value, including any tick-latched
 * change though mBASE is IMMEDIATE so this is a no-op in practice).
 *
 * All arithmetic is byte-addressed. The `m*` register values in
 * reg_values[] are stored as-written (16-bit u16), interpreted directly
 * as byte offsets here. Phase 3's consumption of m* values against the
 * work buffer may apply a /8 halfword convention; that is a separate
 * concern from this advance formula (RESEARCH.md Pitfall 3). */
void spu94_buffer_advance(spu94_state *state) {
    if (!state) return;
    uint32_t mbase = (uint32_t)(uint16_t)state->reg_values[SPU94_REG_mBASE];
    uint32_t advanced = (state->buffer_address + 2u) & 0x7FFFEu;
    state->buffer_address = (advanced > mbase) ? advanced : mbase;
}

/* ADR-0006: snap-on-write. Writing mBASE sets buffer_address to the
 * new mBASE value, immediately. No implicit work-buffer clear.
 *
 * Called from src/spu94/spu94_register_io.c's spu94_set_reg_u16
 * for SPU94_REG_mBASE AFTER the engine layer has updated
 * state->reg_values[SPU94_REG_mBASE] = (int16_t)new_mbase.
 *
 * D-11 seam: this function is the internal side-effect handler.
 * The future Controllers milestone may replace it with an alternative
 * behavior (floor-only, crossfade, clear-and-snap) by re-linking a
 * different translation unit that defines the same symbol. Phase 2
 * keeps the handler internal (not runtime-swappable) per RESEARCH.md
 * Open Question #5 — adding runtime swappability would be additive
 * Controllers-milestone work via a new ADR. */
void spu94_mbase_on_write(spu94_state *state, uint16_t new_mbase) {
    if (!state) return;
    state->buffer_address = (uint32_t)new_mbase;
}

/* Observability accessor (D-23). Exposes the current byte-offset
 * BufferAddress so external observers (Python fuzz harness, witness-diff
 * tooling, Controllers UI) can read it without mutating it. */
uint32_t spu94_get_buffer_address(const spu94_state *state) {
    if (!state) return 0u;
    return state->buffer_address;
}
```

```markdown
## ADR-0006: mBASE write side effect — snap-on-write

**Status:** Accepted (2026-04-19, Phase 2)

**Context:**

Phase 2's discussion identified the mBASE-write side-effect question as a
gray area worth resolving with primary-source research before locking a
behavior. The preliminary CONTEXT.md lean (D-09) was "floor-only — writing
mBASE updates the wrap floor but does not reset BufferAddress." The research
step (see RESEARCH.md § mBASE Side-Effect Evidence) contradicted the
preliminary lean: the nocash psx-spx SPU documentation states in plain
language that an mBASE write additionally sets the current buffer address
to the written value. The wrap formula itself (see this ADR's Decision
section) uses `MAX(mBASE, ...)` so mBASE already acts as a floor on every
subsequent tick — the write-time snap is an additional, stateful side
effect that the formula alone does not produce.

Secondary and tertiary sources (hitmen c02 SPU doc, jsgroth PS1 SPU Part 3
writeup, findable PSX homebrew) are silent on the mid-stream mBASE-write
case, consistent with the Sony BIOS reverb-setup procedure that disables
the reverb before changing registers. GPL witnesses (Mednafen,
lv2-psx-reverb, DuckStation) were not read per PROJECT.md licensing
posture.

**Decision:**

Writing `mBASE` snaps the reverb work-buffer pointer:

```
On any write to mBASE with value N:
    state->reg_values[SPU94_REG_mBASE] = (int16_t)N      (register layer)
    state->buffer_address = (uint32_t)N                  (this ADR)
```

No implicit work-buffer clear. No crossfade. No tick-alignment delay. The
jump can produce an audible discontinuity in the reverb tail; that is
hardware-accurate behavior and SPU-94's default.

BufferAddress advance (once per stereo tick, from `spu94_buffer_advance`
called inside `spu94_tick`):

```
buffer_address = MAX(mBASE, (buffer_address + 2) AND 0x7FFFE)
```

- Byte addressing. The `+2` advances by one 16-bit halfword per stereo tick.
```
